# 猫国建设者本地版：项目结构与数值修改说明

本文对应项目中保留的原版版本 **1.6.1.11**，以本地源码为准。源码提交记录在 [UPSTREAM.txt](../UPSTREAM.txt)。本次只增加说明文档，没有调整游戏平衡或修改当前进度。

## 1. 这个项目由什么组成

项目由原版游戏和本地运行支持两部分组成。建筑、科技树、资源计算、宗教、太空和转生等玩法沿用原版；新增部分负责一键启动、磁盘存档、备份恢复和本地界面。

```text
Cat Nation/
├─ start.cmd                  Windows 启动入口
├─ launcher.mjs               检查服务是否已启动，启动后打开默认浏览器
├─ server.mjs                 本地 HTTP 服务、存档 API、磁盘备份
├─ package.json               根目录启动和存档测试命令，无第三方运行依赖
├─ tests/storage.test.mjs     本地存档测试，使用临时目录
├─ data/
│  ├─ latest.json             当前进度，包含 revision、savedAt、save
│  └─ backups/                历史快照
├─ docs/
│  ├─ 项目结构与数值修改说明.md
│  └─ 玩法攻略.md
└─ game/                     原版源码及本地接入
   ├─ index.html             加载入口，接入 localGame
   ├─ game.js                游戏总控制、效果定义、产出公式、保存、转生
   ├─ core.js                管理器基类、效果汇总等公共机制
   ├─ config.js              语言、主题等基础配置
   ├─ i18n.js                翻译加载和文本查询
   ├─ local-client.js        浏览器与磁盘存档服务的连接
   ├─ local.css              本地存档面板和窄窗口布局
   ├─ js/                    各玩法系统
   ├─ res/                   翻译、样式、图片
   ├─ lib/                   已随源码提供的浏览器依赖
   └─ test/                  上游原版测试
```

游戏计算主要发生在浏览器里。Node.js 服务负责提供文件并保存进度，没有在后台替玩家运行一个独立的游戏模拟器。关闭页面后能否补算进度，由原版的离线进度设置决定。

启动链路：

```text
start.cmd → launcher.mjs → server.mjs → http://127.0.0.1:8765/
    → index.html → 翻译与各系统模块 → GamePage → 游戏循环
```

### 名称、说明和背景文本

以猫薄荷田为例，建筑定义里是：

```js
name: "field",
label: $I("buildings.field.label"),
description: $I("buildings.field.desc")
```

`field` 是程序使用的固定标识，`$I(...)` 根据翻译键取得界面文字。名称、描述和趣味文本常分别对应 `label`、`desc`、`flavor`。

中文翻译的加载顺序是：

1. [res/i18n/en.json](../game/res/i18n/en.json)：英文基础文本和缺失项回退。
2. [res/i18n/zh.json](../game/res/i18n/zh.json)：旧版中文。
3. [res/i18n/crowdin/zh.json](../game/res/i18n/crowdin/zh.json)：后加载的中文，同名键会覆盖前面的内容。

所以只改旧版 `zh.json`，可能看不到变化。个人本地修改应先检查最终生效的键。若以后要向上游贡献翻译，按上游 README 的 Crowdin 流程处理；Crowdin 目录属于上游生成的翻译资源。

**改中文名称通常不改 `name`。** 内部标识被解锁链、公式和存档共同引用；例如把 `field` 改成另一个英文名字，不等于只改了界面标题。

## 3. 数值强度具体在哪里

### 3.1 内容自身的基础数值

以 [buildings.js](../game/js/buildings.js) 中的猫薄荷田为例：

```js
{
    name: "field",
    unlockRatio: 0.3,
    prices: [{ name: "catnip", val: 10 }],
    priceRatio: 1.12,
    effects: { "catnipPerTickBase": 0.125 }
}
```

| 字段 | 含义 | 这里的效果 |
| --- | --- | --- |
| `prices` | 基础建造费用 | 初始费用 10 猫薄荷 |
| `priceRatio` | 数量增长带来的价格倍率 | 每多建一座，下一座基础价格再乘 1.12 |
| `effects` | 对效果系统提供的贡献 | 每座提供 0.125 猫薄荷/tick 的基础产出 |
| `unlockRatio` | 与费用相关的提前显示门槛 | 影响何时出现，不代表只付 30% 的费用 |
| `unlocks` | 建造或研究后解锁哪些内容 | 可解锁建筑、科技、职业、标签页等 |
| `requiredTech`、`evaluateLocks` | 科技或动态条件 | 部分内容另有条件判断 |
| `stages` | 同一个建筑的不同阶段 | 例如牧场与太阳能农场；阶段可有自己的费用和效果 |
| `val`、`on` | 运行时数量 | 常分别用于已建数量和开启数量；属于玩家状态 |

在没有折扣和特殊规则时，第 `n+1` 座建筑的价格约为：

```text
基础价格 × priceRatio^n
```

田地的前三座费用是 10、11.2、12.544 猫薄荷。小屋的基础价格是 5 木材、`priceRatio` 为 2.5，后续会比田地涨得快得多。实际付款还可能包含建筑专属折扣、全局折扣、形而上学减价、虚拟已购数量和挑战规则；正式逻辑在 `getPriceRatioWithAccessor`、`getPricesWithAccessor`。

### 3.2 动态计算的数值

有些 `effects` 开始是 0，然后由 `calculateEffects` 重新赋值。

例如图书馆的阶段静态字段里科学上限是 0，但 `calculateEffects` 为普通图书馆设置的基础效果包含：

```js
"scienceRatio": 0.1,
"scienceMax": 250,
"cultureMax": 10
```

如果要增加图书馆的科学上限，应该检查这里，以及后续天文台、数据中心等对它的修正。只把前面的 0 改为 1000，可能在重新计算后又被覆盖。

冶炼厂更复杂：`calculateEffects` 计算铁产出和木材、矿物消耗，`action` 再根据实际原料供应调整有效运行量。看到一个建筑“面板产出很高但实际没产出”，应同时检查投入原料、开启数量和转换逻辑。

### 3.3 职业强度、人口消耗和仓储

这些数值不都放在建筑表里：

| 目标 | 位置与字段 |
| --- | --- |
| 伐木工基础产量 | `village.js` → `jobs` → `woodcutter` → `modifiers.wood = 0.018` |
| 农民基础产量 | `village.js` → `farmer` → `modifiers.catnip = 1` |
| 学者基础产量 | `village.js` → `scholar.calculateEffects` → `science = 0.035` |
| 每猫基础食物消耗 | `village.js` → `catnipPerKitten = -0.85`，单位为每 tick |
| 游戏基础仓储 | `buildings.js` → `effectsBase`，例如初始木材上限 200、猫薄荷上限 5000 |
| 仓储建筑增加的容量 | 对应建筑的 `effects` / `calculateEffects` |
| 最终仓储上限 | `resources.js` → `updateMaxValue` 及相关上限倍率方法 |
| 合成投入 | `workshop.js` → `crafts` → `prices` |
| 合成加成 | `game.js` → `getCraftRatio`、`getResCraftRatio`，以及相应升级和建筑效果 |

### 3.4 “每 tick”和“每秒”的区别

`game.js` 的 `ticksPerSecond` 默认是 **5**。在普通速度下：

```text
每秒基础值 = 每 tick 基础值 × 5
```

因此，一块田的未修正基础产量为 `0.125 × 5 = 0.625/秒`。春天无天气修正时乘 1.5，显示约 0.94/秒；普通冬天乘 0.25，只剩约 0.15625/秒。寒冷天气会进一步改变季节倍率。

一个农民的未修正基础值为 5 猫薄荷/秒，一个伐木工为 0.09 木材/秒。最终还要计算幸福度、技能、工具、建筑、宗教、转生奖励等影响。**面板净产出还扣除了消耗，不能拿基础产量直接当最终值。**

不建议为了“全局加速”直接修改 `ticksPerSecond`：它还关联人口成长、耗粮、事件、自动保存等节奏。若以后要做倍速功能，应作为单独功能设计和验证。

### 3.5 最终公式和效果汇总

实际强度主要沿下面的路径生效：

```text
建筑 / 职业 / 升级 / 宗教 / 太空 / 政策等数据
  → 各管理器提供效果、更新效果缓存
  → game.getEffect(...) 取得汇总效果
  → 产出、消耗、价格和仓储公式分别计算
  → 资源池更新数量，界面显示结果
```

关键入口：

- `core.js` 的管理器效果汇总逻辑。
- `game.js` 的 `calculateAllEffects`、`getResourcePerTickStack`、`getResourcePerTick`。
- `game.js` 的效果说明表：搜索效果键，例如 `woodJobRatio`，可帮助理解含义。
- `game.js` 的 `getLimitedDR` 等收益递减函数。
- `resources.js` 的容量计算与资源增减逻辑。

`catnipPerTickBase`、`woodJobRatio`、`scienceMax` 是不同类型的效果键。不能简单认为所有加成都相加，也不能认为全部建筑产量都被所有全局倍率放大。

季节与农民就是一个例子：`getResourcePerTickStack` 中，季节天气倍率作用于前面的基础生产部分，村庄职业产出在后面加入。因此不能把春季的整条猫薄荷净产出直接乘一个比例来估算冬季净产出。

## 4. 如果想修改数值，具体怎么找

以下是修改方法示例，**没有替你应用这些平衡改动**。

| 想达到的效果 | 建议寻找的位置 | 同时检查 |
| --- | --- | --- |
| 猫薄荷田基础产量翻倍 | `field.effects.catnipPerTickBase`：0.125 → 0.25 | 春冬变化、养猫成本、农民的相对价值 |
| 小屋前期便宜一些 | `hut.prices` 与 `hut.priceRatio` | 降基础价影响开局；降增长倍率对大量建造影响更大 |
| 每猫少吃一点 | `VillageManager.catnipPerKitten` | 它是负数；-0.85 → -0.6 才是减少消耗 |
| 图书馆能存更多科学 | `library.calculateEffects` 中的 `scienceMax` | 普通阶段和数据中心阶段的分支 |
| 木梁更容易合成 | `crafts` 中 `beam.prices` | 合成加成会进一步放大收益 |
| 更早解锁某建筑 | 科技 `unlocks`、建筑条件与显示门槛 | 已有存档中保存的解锁状态 |
| 提高钛交易收益 | `diplomacy.js` 的斑马钛概率及数量公式 | 船只、交易量和关系加成 |
| 更强的长期奖励 | `prestige.js` 的升级效果及 `game.js` 的转生规则 | 普通一周目和多周目增长差别很大 |

建议流程：手动备份并导出当前进度 → 每次只改一个目标 → 刷新页面 → 在隔离测试存档里比较原始值、面板值和实际消耗 → 满意后再继续正式进度。改过数值后已经产生的资源，不会因为把源码改回去而自动扣除。

搜源码可以使用：

```powershell
rg -n 'name: "field"|catnipPerTickBase' game/js/buildings.js
rg -n 'name: "hut"|maxKittens' game/js/buildings.js
rg -n 'name: "beam"|crafts:' game/js/workshop.js
rg -n 'catnipPerKitten|name: "woodcutter"' game/js/village.js
```

## 5. 存档放了什么，和规则有什么区别

`data/latest.json` 大致是这个结构，示例值仅说明格式：

```json
{
  "revision": "某次保存的唯一版本号",
  "savedAt": "保存时间",
  "save": {
    "resources": [],
    "buildings": [],
    "calendar": {},
    "village": {},
    "science": {},
    "workshop": {},
    "religion": {},
    "space": {},
    "time": {},
    "game": {}
  }
}
```

这里记录你拥有的资源、建筑数量、人口分工、研究状态、日期和设置等。基础产出、价格增长和配方等规则主要从源码重新加载。

因此，“把已有木材改成 10000”和“提高伐木工产量”是两件事：前者改玩家进度，后者改全局规则。已有资源数量还会受到仓储和加载逻辑影响。

原版保存的 `forceLZ`、压缩文本导入等仍有自己的处理；本地磁盘服务保存的是外面带版本号的 JSON 封装。原版导出的纯存档应使用导入按钮，不能直接拿来覆盖带封装的 `latest.json`。

## 6. 本地存档支持如何工作

启动时 `local-client.js` 先请求 `/api/state`，优先把磁盘进度放进原版读取的浏览器存储，然后原版正常加载。磁盘文件不存在时保留同一浏览器中的副本；显式开启新游戏则使用新的空状态。

之后它接入 `game.save()`，使用一个按实际时间运行的自动保存定时器（默认 15 秒）。地图顶部与存档管理中的下拉框可以修改间隔，偏好写入浏览器的 `cat-nation.local.autosave-seconds`，切换后清除旧定时器并重新计时。原版按游戏 tick 计数的自动存档由此定时器接管，避免加速游戏或较长间隔时发生重复保存。浏览器把进度发送给 `server.mjs`，服务端先检查格式和存档版本，再写入磁盘。

| 接口 | 作用 |
| --- | --- |
| `GET /api/health` | 启动器识别已运行的本地服务 |
| `GET /api/state` | 读取当前磁盘进度 |
| `POST /api/save` | 保存、手动备份、导入、恢复、转生或新游戏 |
| `GET /api/backups` | 列出历史文件 |
| `GET /api/backup/<文件名>` | 读取指定备份 |

每次提交携带 `revision`。如果另一个窗口已保存，旧版本提交会被拒绝；旧窗口暂停，并提示刷新。写文件时先写临时文件、同步内容再改名，以减少半截 JSON 覆盖正常存档的风险。

自动快照按保存触发，间隔至少一分钟，保留最近 240 份；并非后台每到整分钟就独立生成文件。手动快照以及导入、恢复、转生和新游戏前的保护快照长期保留。

转生需要专门接入：原版 `_resetInternal` 生成下一周目的存档；本地版先备份本周目，再把下一周目的结果写到磁盘，成功后才刷新。否则启动时的磁盘恢复可能把转生结果覆盖回去。

这些措施保护本机进度，但都位于同一硬盘。跨设备备份请导出文件，或另行复制 `data` 到其他存储位置。

## 7. 已验证范围和继续开发入口

根目录 `npm test` 检查的是新增存档服务，覆盖真实原版格式的保存、服务重启读取、备份恢复、格式拒绝、并发版本冲突、转生/新游戏保护及访问边界。它不代表运行了上游所有玩法测试。

前一轮已在浏览器实测采集、建田、自动生产、手动备份、刷新续玩、转生和备份恢复。修改经济系统后，应按具体改动补充上游 `game/test` 风格的玩法验证。

如果以后想做自己的内容，建议从单个建筑或工坊升级开始：定义内部标识与费用 → 加翻译键 → 接入解锁链 → 检查效果如何被汇总 → 验证保存/加载和转生。新增资源时还需要检查资源注册、容量和转生保留规则。
